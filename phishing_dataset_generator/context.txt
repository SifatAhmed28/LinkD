# Context: Synthetic Phishing Dataset Leakage / Generator Fixes

I am building a **synthetic phishing-vs-legitimate webpage dataset** for ML phishing detection. The dataset is generated by Python code and exported as `dataset_meta.csv`.

The current ML models are performing suspiciously well, which indicates that the synthetic generator is leaking the class label through deterministic structural differences between phishing and legitimate pages.

The objective is **NOT simply to remove useful ML features**. The main objective is to fix the generators so that legitimate and phishing samples have realistic overlap, allowing features such as domain mismatch, password fields, form actions, TLD risk, etc. to remain useful without becoming near-perfect proxies for the label.

## Main files

Relevant generator files include:

* `generators/phishing_page.py`
* `generators/legitimate_page.py`
* `generators/legit_phish_utility.py`
* `generators/feature_extractor.py`
* `generators/attacker_domains.py`
* `generate_dataset.py`
* possibly `html_builder.py`
* possibly `legitimate_variations.py`
* possibly `phishing_variations.py`

The dataset currently has 500 phishing and 500 legitimate samples in the test dataset I inspected.

## Dataset structure

The CSV was originally ordered approximately as:

1. column names
2. all phishing rows
3. all legitimate rows

However, this is **not the cause of the performance problem**, because `train_test_split(..., stratify=y, random_state=42)` shuffles by default.

An explicit shuffle may still be added for clarity:

```python
df = df.sample(
    frac=1.0,
    random_state=42
).reset_index(drop=True)
```

but this does not fix the leakage.

## Major leakage/problematic features found

### 1. `form_action_brand_domain_mismatch`

Observed:

```text
label 0:
False = 100%

label 1:
True = 100%
```

This is a perfect label proxy.

The model can literally learn:

```python
if form_action_brand_domain_mismatch:
    phishing
else:
    legitimate
```

This is currently the worst leakage feature.

The generator must be changed so this feature has realistic overlap across both classes.

### 2. `page_brand_domain_mismatch`

Observed:

```text
label                           0      1
False                        0.502   0.000
True                         0.498   1.000
```

Every phishing page currently has `page_brand_domain_mismatch=True`.

Legitimate third-party-hosted pages can also have mismatch, which is good, but `False` currently implies legitimate with 100% certainty.

This feature needs overlap on both sides or needs to be excluded from training until generation is fixed.

### 3. `form_action_type`

Observed:

```text
                                  legitimate   phishing

empty                               56.4%        0.0%
official_brand_cross_origin         21.4%        0.0%
same_origin                         22.2%       51.2%
same_platform_cross_origin           0.0%       48.8%
```

The distributions are almost disjoint.

The generator should support realistic overlap among values such as:

```text
same_origin
relative
empty
about_blank
javascript
mailto
same_platform_cross_origin
official_brand_cross_origin
external_cross_origin
```

The exact probabilities should be realistic rather than arbitrary, but no category should effectively reveal the class.

## Important issue with `no form` vs `empty action`

In `feature_extractor.py`, the current logic is approximately:

```python
form_action = forms[0].get("action", "") if forms else ""
```

This collapses two different cases:

```html
<form action="">
```

and:

```html
<!-- no form exists at all -->
```

into:

```text
form_action = ""
```

Then `classify_form_action()` classifies both as:

```text
empty
```

This is semantically wrong.

The desired behavior is:

```text
No form                        -> no_form
<form action="">               -> empty
<form action="about:blank">    -> about_blank
<form action="javascript:..."> -> javascript
<form action="mailto:...">     -> mailto
<form action="/login">         -> relative
```

Recommended extractor change:

```python
has_form = bool(forms)

form_action = (
    forms[0].get("action", "")
    if forms
    else None
)

form_method = (
    forms[0].get("method", "get")
    if forms
    else None
)
```

and `classify_form_action()` should treat:

```python
if form_action_url is None:
    return "no_form"
```

before checking empty strings.

## 6. `html_num_forms`

Potentially highly predictive because phishing pages appear to be almost universally login/form pages, while legitimate pages include:

```text

landing
about
docs

```

This creates a structural class imbalance.

The model may effectively learn:

```text

```

The negative class should therefore contain many legitimate login/authentication pages.

## Major dataset design flaw: phishing pages vs mixed legitimate page types

Phishing samples are overwhelmingly login/credential-collection style pages.

Legitimate samples include:

```text
login
landing
about
docs
blog
```

Even if `page_type` is removed from the CSV, the model can reconstruct page type using:

```text

html_num_password_inputs
credential_keyword_score
visible_text
body_visible_text
document_title
url_num_sensitive_words
html_num_hidden_inputs
```

For a meaningful phishing-login classifier, a much stronger comparison is:

```text
phishing login pages
vs
legitimate login/authentication pages
```

rather than:

```text
phishing login pages
vs
login + blog + docs + landing + about
```

Legitimate negatives should contain plenty of:

```text

forms
hidden inputs
login/signin words
credential-related terms
JavaScript
complex HTML
relative actions

```


This is another major class distribution difference.

Notably:

```text

```

while phishing reaches:

```text
1.0
```

So any value above `0.026` currently guarantees phishing in this generated dataset.

`tld_risk_score` itself is not necessarily a bad real-world feature. The problem is the synthetic distribution.

The generator should use TLDs such that legitimate and phishing distributions overlap more realistically.

## TLD normalization

TLD phishing scores are intended to range from `0` to `1`.

The correct normalization chosen was maximum scaling:

```python
max_score = max(tld_weights, default=0)

if max_score > 0:
    tld_weights = [
        score / max_score
        for score in tld_weights
    ]
```

NOT:

```python
score / sum(scores)
```

because the latter makes the values sum to 1 rather than making the highest risk equal to 1.

Potential additional problem:

```python
TLD_RISK.get(tld, MAX_TLD_RISK)
```

means an unknown TLD gets the maximum possible risk.

This can create artificial phishing-only values.

Please inspect whether unknown TLDs should instead use:

* median risk,
* mean risk,
* explicit unknown flag,
* a neutral/default risk,
* or another statistically justified fallback.

Do not automatically assume unknown means maximum phishing risk.

## Legitimate TLD risk generation

Legitimate pages now also receive `tld_risk_score`.

For legitimate first-party:

```python
tld = real_domain.split(".")[-1]
```

For legitimate third-party:

```python
tld = platform_domain.split(".")[-1]
```

Then:

```python
tld_risk_score = get_tld_risk(tld)
```

This is stored in metadata.

## `real_domain` mapping for legitimate form actions

A helper can conceptually behave like:

```python
def generate_legitimate_form_action(
    real_domain: str,
    action_type: str,
) -> str:

    path = random.choice([
        "login",
        "signin",
        "log-in",
        "sign-in",
    ])

    if action_type == "same_origin":
        return f"https://{real_domain}/{path}"

    if action_type == "relative":
        return f"/{path}"

    if action_type == "empty":
        return ""

    if action_type == "about_blank":
        return "about:blank"

    if action_type == "javascript":
        return "javascript:void(0)"

    if action_type == "mailto":
        return f"mailto:support@{real_domain}"

    raise ValueError(
        f"Unknown form action type: {action_type!r}"
    )
```

But the final generation probabilities should be chosen carefully to produce realistic overlap, not simply arbitrary noise.

## ML pipeline raw text issue

The current Colab code does NOT directly one-hot encode full:

```text
url
form_action
visible_text
parsed_forms
body_visible_text
document_title
url_path
```

because doing that would create extremely high-cardinality dummy variables and encourage memorization.

Instead, basic derived numeric properties such as length, digit count, special-character count, etc. were generated.

However, the final intended system may later use appropriate NLP/URL encoders separately.

## Evaluation methodology problem

A random row split may still overestimate performance because generated pages from the same brand/template family can appear in both training and testing.

For example:

```text
train:
Facebook synthetic variation A
Google synthetic variation A

test:
Facebook synthetic variation B
Google synthetic variation B
```

The model may identify template families rather than learn general phishing behavior.

A better validation scheme should include at least one of:

### Brand holdout

Train on some brands and test on completely unseen brands.

Use something like:

```python
from sklearn.model_selection import GroupShuffleSplit

groups = df["brand"]

splitter = GroupShuffleSplit(
    n_splits=1,
    test_size=0.2,
    random_state=42,
)

train_idx, test_idx = next(
    splitter.split(
        df,
        df["label"],
        groups=groups,
    )
)
```

### Template-family holdout

If samples are generated from shared HTML templates, samples from the same base template should not appear in both train and test.

### Generator-strategy holdout

Optionally test whether the detector generalizes to phishing strategies not seen during training.

### Real-world external validation

Ultimately the synthetic-trained model should be tested on independent real phishing and legitimate webpages, because synthetic-vs-synthetic evaluation can remain misleading even after leakage fixes.

## Important philosophy for fixing the dataset

Do NOT solve the problem by blindly deleting every strong feature.

Features such as:

```text
domain mismatch
form action type
password inputs
TLD risk
credential keywords
form counts
```

are legitimate phishing-detection signals.

The problem is that the synthetic generator currently makes some of them deterministic or almost deterministic.

The desired state is:

```text
P(feature | phishing) != P(feature | legitimate)
```

so the feature is useful, but:

```text
P(feature | phishing) != 1
P(feature | legitimate) != 0
```

for simplistic binary cues.

There should be realistic overlap.

Example conceptual target:

```text
has password field:

legitimate -> maybe 60-80% for auth/login negatives
phishing   -> maybe 75-95%
```

rather than:

```text
legitimate -> 43.6%
phishing   -> 100%
```

Likewise, form-action categories should occur in both classes where semantically plausible.

## Immediate task for the next AI/session

Please inspect the generator code and systematically fix the synthetic dataset so that:

1. `form_action_brand_domain_mismatch` is no longer perfectly equal to the label.
2. `page_brand_domain_mismatch` has meaningful overlap across both classes.
3. `form_action_type` categories overlap realistically.
4. `no_form` is distinguished from an explicitly empty form action.
5. Password fields/counts do not perfectly identify phishing.
6. Legitimate negatives include many realistic login/authentication pages.
7. Phishing pages are not all structurally identical login pages.
8. `tld_risk_score` distributions overlap more realistically.
9. Unknown TLD handling does not automatically create maximum-risk phishing-only values unless justified.
10. Hidden-input counts and form counts do not trivially separate the generators.
11. Text-injection features do not become deterministic class markers.
12. Raster-overlay structural features are balanced across both classes.
13. No generator provenance/annotation fields are used as ML inputs.
14. Evaluation uses group/brand/template holdouts in addition to random splits.
15. After changes, report class-conditional distributions for each important feature before training.

The goal is not to force model performance downward arbitrarily. The goal is to make the synthetic classification task scientifically meaningful and prevent the model from learning generator fingerprints instead of phishing behavior.
